# Abstract

The CUDA 11.8 upgrade path is now working for both local training and local evaluation on ForeSight without changing the project's `mmcv 1.x` / `mmdet 2.x` code path. The current local validation covers short distributed `train.py` and `test.py` runs using the `foresight_cuda118` image through `scripts/local_run.sh`.

The remaining gap is a full remote evaluation run to confirm that metrics match the existing environment and that the upgraded image behaves correctly on the target servers.

# Intro

This report records the initial CUDA 11.8 upgrade for ForeSight. The main motivation is compatibility with newer GPUs, especially H100-class systems such as Trillium and Killarney, without forcing an immediate migration to `mmcv 2.x` / `mmdet 3.x`.

The upgrade keeps the current code path intact by using a conservative stack around `mmdet 2.x`, `mmcv-full 1.x`, the local CUDA ops, and `flash-attn`. A separate image and wrapper were added so the CUDA 11.8 path can be validated in parallel with the existing local workflow.

# Method

The new container was added at `docker/Dockerfile.cuda118` and built as `foresight_cuda118`. The stack was pinned as follows:

| Component | Old path | CUDA 11.8 path |
| --- | --- | --- |
| CUDA | Older local image | `11.8` |
| Python | Existing repo path | `3.8` |
| PyTorch | Older local image | `2.0.1+cu118` |
| torchvision | Older local image | `0.15.2+cu118` |
| torchaudio | Older local image | `2.0.2+cu118` |
| mmcv | Existing `1.x` stack | `mmcv-full 1.7.2` |
| mmdet | Existing `2.x` stack | `2.28.2` |
| flash-attn | Existing project dependency | `2.3.2` |

The key implementation changes were:

- Add a separate CUDA 11.8 Dockerfile and build path.
- Keep the existing OpenMMLab major versions instead of migrating frameworks.
- Make the deformable aggregation extension import more robust for bind-mounted repo use.
- Update `tools/train.py` and `tools/test.py` to accept both `--local_rank` and `--local-rank`, which is required for the newer PyTorch distributed launcher path in the CUDA 11.8 container.
- Consolidate local Docker execution into `scripts/local_run.sh`, with image selection via `IMAGE_NAME=...`.
- Default local runs to `WANDB_MODE=offline` to avoid W&B init stalls caused by container-side DNS issues during local execution.

Validation was staged from imports to real execution. The first local smoke test used `projects/configs/sparsedrive_r50_stage2_1gpu_bs2.py` with `runner.max_iters=2`, `--no-validate`, and reduced loader settings. That run completed `Iter [1/2]` and `Iter [2/2]` and saved `iter_2.pth`, which showed that the CUDA 11.8 stack could complete a short distributed training run.

After that initial smoke test, the standard local wrapper path was re-validated with the production-style commands:

- `IMAGE_NAME=foresight_cuda118 ./scripts/local_run.sh bash ./tools/dist_train.sh projects/configs/sparsedrive_r50_stage2_1gpu_bs2.py 1 --deterministic`
- `IMAGE_NAME=foresight_cuda118 ./scripts/local_run.sh bash ./tools/dist_test.sh projects/configs/sparsedrive_r50_stage2_1gpu_bs2.py ckpt/sparsedrive_stage2.pth 1 --deterministic --eval bbox`

Both commands started correctly under the CUDA 11.8 image. The training command ran for multiple iterations, and the evaluation command entered dataset iteration successfully. This is enough to conclude that the local CUDA 11.8 path now supports the standard distributed train and eval entrypoints for this config.

# Results

The local CUDA 11.8 path is functional for the following scope:

- Container startup with the new image `foresight_cuda118`
- Distributed launch through `tools/dist_train.sh` and `tools/dist_test.sh`
- Short training execution on `projects/configs/sparsedrive_r50_stage2_1gpu_bs2.py`
- Evaluation startup on `ckpt/sparsedrive_stage2.pth` with `--eval bbox`

The main issue found during validation was compatibility between the newer PyTorch launcher behavior and the repo entrypoints. In the CUDA 11.8 container, `torch.distributed.launch` passed `--local-rank`, while the repo scripts only accepted `--local_rank`. Updating both entrypoints to accept both forms removed that failure mode.

An additional environment issue was observed with W&B in the local Docker path. The host machine could reach W&B, but the container could not reliably resolve W&B hostnames, leading to initialization timeouts. For local CUDA 11.8 runs, the wrapper now defaults to offline W&B mode.

# Discussion

At this point, the CUDA 11.8 migration looks viable as an incremental environment update rather than a framework migration. The repo can still run on the existing `mmcv 1.x` / `mmdet 2.x` stack, and the local validation no longer depends on a separate one-off wrapper script.

The remaining technical uncertainty is not whether the code launches, but whether a full evaluation on a server reproduces the expected metrics and runtime behavior. That is the next meaningful checkpoint before making the CUDA 11.8 image the default local path or using it more broadly on newer hardware.
