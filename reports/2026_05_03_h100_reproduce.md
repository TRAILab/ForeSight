# H100 reproducibility diagnostic — Tamia, Fir, Rorqual vs Killarney

2026-05-03

## Summary

Cross-cluster reproducibility holds for `_evalmatchmode` and `_streamc`. It **fails on `_egostatus` CR** specifically: planning L2 reproduces within noise on every cluster, but `obj_box_col` is elevated 2–6× on the three H100 clusters relative to the canonical Killarney L40S read. The drift is deterministic (Tamia hits exactly 0.243% twice on independent runs), affects only the egostatus configuration, and is not explained by hardware alone (the same H100s reproduce streamc and evalmatchmode cleanly). The most legible environmental difference is **PyTorch 2.0.1 (Killarney) vs 2.1.2 (H100 clusters)** sitting on top of identical CUDA 11.8 and the same stage-1 ckpt — but a single-layer attribution to the egostatus MLP+broadcast-add is **not supported by the data** (see "What's wrong with the broadcast-add story" below).

The Killarney L40S read remains the canonical comparator until we run the diagnostics in the last section.

## What's wrong with the "egostatus broadcast-add is the cause" story

An earlier framing pinned the cross-cluster CR drift on the egostatus MLP+broadcast-add path specifically. That story does not hold up:

1. **The op is too boring to drift.** The egostatus encoder is `nn.Linear(5, 256) → ReLU → nn.Linear(256, 256)`, then a broadcast-add to `plan_mode_query`. None of these ops have changed materially between PyTorch 2.0.1 and 2.1.2 — Linear is GEMM, ReLU is elementwise, broadcast-add is elementwise. There is no documented numerics regression in any of these between those minor versions. Blaming this layer is hand-waving.
2. **Streamc uses the same broadcast-add and is clean.** Streamc inherits egostatus's broadcast-add at init *and* per-stage. If the broadcast-add itself were the failing op, streamc CR should drift too. It doesn't (Δ ≤ 0.006 pp on Fir/Rorqual). So whatever drifts is not the broadcast-add per se.
3. **The differential between egostatus and streamc is the agent path, not the broadcast-add.** Streamc adds `ego_only_planning=True` (drops agent slots from the planner) and `image_at_det` (replaces the conflict head's `agent_features` input with image features sampled at det BEV positions). The broadcast-add is held constant. So the egostatus-only drift must come from a code path that streamc bypasses — i.e. the agent-aware decoder layers and / or the agent-feature → conflict-head signal that feeds rescore.

The honest read is that **we know egostatus is the affected configuration; we do not know which op inside it is responsible.**

## What the data actually constrains

- **L2 reproduces under PyTorch 2.0.1 → 2.1.2 + L40S → H100.** Whatever drifts does not move the trajectory enough to matter for averaged-distance metrics.
- **`_streamc` reproduces too.** The deformable cross-attention to image features, the planning decoder backbone, and the (modified) conflict head all run cleanly cross-cluster. So image-features path + ego-only planning + image-at-det conflict head are all numerically stable.
- **CR is the sensitive metric.** It thresholds a continuous trajectory perturbation into a binary collision count over ~1.4 M box checks; sub-mm trajectory drifts can flip a non-trivial number of marginal cases either way. This is generic to CR, not to egostatus.
- **Egostatus is the only configuration that exercises the agent-aware refinement path while having a low absolute CR baseline (~0.04%).** Evalmatchmode also runs the agent path but at higher absolute CR (~0.05%), so a same-magnitude absolute drift looks proportionally smaller; streamc runs egostatus but bypasses the agent path. Egostatus + agent-path-active + low-CR-baseline is the cell where drift is visible.

## Numerical-resolution view: what FP-op differences are real, and is CR sensitivity the cause or the compounder?

### What FP-op differences exist between the two stacks

**Hardware (L40S sm_89 → H100 sm_90):**
- TF32 matmul = 10-bit mantissa input × FP32 accumulate, vs FP32's 23-bit mantissa. For activations in [-2, 2], TF32 effective resolution ~1e-3, FP32 ~1e-7 — ~13 bits / ~4 decimal digits dropped per matmul. *Availability* of TF32 is the same on L40S and H100; what differs is throughput (H100 tensor cores are wider, cuBLAS dispatches to TF32 kernels more aggressively) and tile/reduction layout (different summation order → different rounding).
- cuBLAS picks an sm-specific kernel for the same `nn.Linear`. Different tile sizes and inner-product orderings produce bit-different outputs even with TF32 off and identical inputs. Independent of PyTorch version.
- Online-softmax in attention normalizes across tiles; tile size depends on hardware. Bit-identical only when single-tile.
- H100 atomic-add throughput differs from L40S; some PyTorch ops use atomics under the hood. `--deterministic` suppresses non-deterministic *algorithms*, but does NOT force FP32 over TF32 or pin tile sizes — TF32 is controlled by a separate flag (`torch.backends.cuda.matmul.allow_tf32`).

**Software (PyTorch 2.0.1 → 2.1.2):**
- SDPA backend dispatch heuristics shifted. 2.1 made flash / mem-efficient backends more aggressive on Ampere+; flash-attn needs fp16/bf16 inputs so for FP32 inputs the fallback usually picks mem-efficient or math, but the heuristic order changed → different backend → different reduction order and intermediate precision.
- Default `allow_tf32` and autocast policies moved between minor versions; worth measuring on each cluster: `python -c "import torch; print(torch.backends.cuda.matmul.allow_tf32, torch.backends.cudnn.allow_tf32)"`.
- cuBLAS wrapper changes in 2.1 alter the algorithm hint passed to cuBLAS, sometimes selecting a different kernel.

None of these act on the egostatus `Linear → ReLU → Linear → broadcast-add` itself; all of them act on attention / Linear ops in the agent-aware decoder path that streamc bypasses.

### Is CR sensitivity the cause or the compounder?

**Compounder, but not the full story** — and the answer differs by cluster.

CR thresholds a continuous overlap at zero across ~1M box checks. A trajectory perturbed by ε flips marginal collisions within ε of the threshold. L2 drift across clusters is 0.001–0.005 m, i.e. sub-mm to a few mm of average trajectory drift. Sub-mm is enough to flip ~2× of marginal collisions if near-miss density is realistic for nuScenes; **6× requires either much larger ε or a systematic bias** (not zero-mean noise).

- **Fir CR is noisy across seeds (0.048%, 0.087%) — Δ ≈ 2.5× our Killarney noise floor.** Two independent same-config Fir reads give a wide spread. The "Fir is consistently elevated" reading was a single-seed artifact; the true Fir distribution may have mean ~0.06% with high variance, or it may be sampling from the canonical band most of the time with occasional excursions. Either way, **a single-point Fir CR read cannot be used to draw a numerical conclusion** about the H100 effect.
- **Rorqual CR is also noisy across seeds (0.094%, 0.119%, 0.131%).** Mean ~0.11%, spread ~0.04 pp.
- **Tamia 6.1× deterministic (270279 + 272454 both hit exactly 0.243%).** Not consistent with random ε amplification. Random noise would not reproduce the exact same CR. This requires either larger ε *or* a systematic perturbation direction. CR sensitivity alone is **not** sufficient.

**So the picture is two phenomena, not one:**
1. **Fir / Rorqual: high CR variance under PyTorch 2.1.2 / H100.** Mean may be ~canonical or ~2× canonical; we don't have enough seeds to tell. CR-sensitivity-as-amplifier of small numerical perturbations naturally produces a high-variance distribution if those perturbations themselves have stochastic components (e.g. NCCL collective reduction order, atomic op ordering during eval). What L40S delivers as a tight 0.040 ± 0.007 distribution, H100 may deliver as 0.06 ± 0.04.
2. **Tamia: systematic offset.** Same software stack as Fir; mean is 6× canonical and *deterministic*. CR sensitivity carries no signal here — there's a real systematic perturbation that reproduces bit-for-bit. Same H/W family as Fir/Rorqual, so the cause is in the runtime layer: H100 driver version, NCCL pinning, libnuma / CPU-pinning under SciNet's scheduler, or the extra ckpt bind.

**Implication for the paper:** the H100-vs-L40S CR delta is **noisy, not biased**, on Fir and Rorqual — at least with the data in hand. A multi-seed mean on those clusters could land at canonical levels. Tamia is the only cluster where we can confidently say CR is "broken." The TF32 / SDPA / torch-pin diagnostics still target the H/W-induced variance source, but with the noise band wider than our point estimates, **multi-seed comparisons are necessary** to draw conclusions — single eval-only reads are not enough.

## Plausible mechanisms (none confirmed)

1. **SDPA backend dispatch in agent-aware attention.** PyTorch 2.1 expanded `scaled_dot_product_attention` backend selection (flash, mem-efficient, math) and changed dispatch heuristics. On H100 the flash-attn path is more aggressive than on L40S. If any agent self-attention or agent↔ego cross-attention is dispatched to a different SDPA backend on PyTorch 2.1.2 / H100, you get bit-different attention outputs that propagate into per-mode trajectories and the rescore signal. This is the mechanism with the cleanest fit to "agent path drifts, image+ego paths don't" — but we have not measured it.
2. **TF32 defaults amplifying small upstream errors on H100.** H100 has higher TF32 throughput than L40S; the same `allow_tf32=True` default flips small accumulation differences that average out on L40S into bigger excursions on H100. The agent-aware attention has many GEMMs that would multiply this effect through the decoder stack.
3. **mmcv source-build vs wheel.** The H100 mmcv was rebuilt from source with a `_get_stream(device)` patch to fix a PyTorch 2.x stream API incompatibility. That patch is in `mmcv/parallel/_functions.py` — a data-distribution helper, not a numerics op. But a source build also picks up whatever the build environment's CUDA/CUDNN/TF32 flags are, which can subtly differ from the wheel's. Less likely than #1/#2 but not ruled out.
4. **Tamia's 3× excess over Fir/Rorqual.** Same container, same PyTorch, same git, same CUDA, same H/W family. Differences are limited to: SciNet vs Alliance scheduler / NCCL pinning, H100 driver version (could not query from login), the extra ckpt bind. No clear mechanism. The exact-twice 0.243% is the most suspicious part — points to a deterministic systematic error, not stochastic noise.

| Hypothesis | Status |
|---|---|
| Hardware (H100 vs L40S) alone | Insufficient — same H/W reproduces streamc + evalmatchmode |
| **PyTorch 2.0.1 → 2.1.2** (esp. SDPA dispatch / TF32 fast paths) | **Most likely primary, not yet isolated** |
| TF32 defaults amplifying on H100 | Likely amplifier on top of #1; testable in 1 h |
| mmcv source build vs wheel | Possible secondary |
| Egostatus MLP / broadcast-add itself | **Unsupported** — too boring to drift; streamc uses it cleanly |
| Stage-1 ckpt drift | Ruled out (md5 match) |
| CUDA 11.8 itself | Ruled out (identical) |
| Setup bugs (binds, writable-tmpfs) | Ruled out as primary (don't track CR direction) |
| Code drift in `sd_combined` branch | Ruled out (commits on agent path are inert; `95db051` is on every cluster) |
| Tamia-specific 3× excess over Fir/Rorqual | **Open** — same software stack, different scheduler/driver/bind |

## What we should run (cheapest first)

**Important methodological update (after 38378856 landed):** Single-point CR reads on Fir/Rorqual cannot resolve any of these hypotheses because the noise band is wider than the effect size. Each diagnostic below should be run **across at least 2–3 seeds** to get a distribution.

1. **Disable TF32 on Fir egostatus eval** (`FORESIGHT_DISABLE_TF32=1` env var added to `tools/test.py`). Submitted as Fir 38503552 (running 2026-05-03 PM) on the existing Fir-trained ckpt. **Read in distribution against the Fir 2-seed baseline (0.048%, 0.087%, mean 0.068%).** If TF32-off delivers a tight ~0.04 distribution across seeds, TF32 was driving the variance and the production fix is to disable TF32 on H100 clusters. If TF32-off lands inside the existing Fir band, TF32 is null.
2. **K-trained ckpt, Fir eval, default TF32** (Fir 38504768 in flight). Isolates eval-time vs training-time numerics: same K-ckpt that gives 0.040% on Killarney, evaluated on Fir. If it lands inside the Fir noise band, eval-time numerics are responsible (training is fine). If it lands at canonical, training-time was responsible (the Fir-trained ckpt has slightly different weights).
3. **Force SDPA math backend on Fir egostatus eval.** Wrap the agent-aware attention forward in `with torch.backends.cuda.sdp_kernel(enable_math=True, enable_flash=False, enable_mem_efficient=False):`. If the math backend gives a tight CR distribution while the default backend is wide, dispatch heuristics are the mechanism. Targets the actual code path the data points at.
4. **Pin PyTorch 2.0.1 in `Dockerfile.cuda118pytorch21`** and rebuild. If the H100 egostatus CR distribution narrows to Killarney's, the PyTorch minor-version delta is the primary cause and we can converge to a single canonical container across all clusters. ~1 day to rebuild + push + test on Fir.
5. **Tamia residual.** Once #1–#4 characterize the H100-vs-L40S behavior, compare Fir and Tamia from the *same* ckpt under the same PyTorch / TF32 settings, multi-seed. Whatever's left is Tamia-specific. Candidates: H100 driver version, NCCL collective ordering during eval, libnuma / CPU-pinning under SciNet's scheduler.

## Practical implications for the paper

- The headline (`_egostatus`, K/V-off paper architecture, L2=0.3692/CR=0.040%) is a Killarney L40S read. **L2 is portable across all clusters.** **CR is not portable on this specific config until we close the diagnostic above.**
- `_evalmatchmode` and `_streamc` are portable on both metrics; cross-cluster reproductions of those configs are valid.
- For now, when running egostatus jobs cross-cluster, treat L2 as comparable and CR as cluster-conditioned. Do not stack H100 egostatus CR reads with L40S egostatus CR reads in the same mean.
- The `minS2` claim is locked on Killarney; it should not be confirmed cross-cluster on H100 until we know whether minS2 inherits the agent-path drift (it shouldn't — minS2 includes Stream C / `ego_only_planning` — but we should test it once before relying on H100 reads).
