## Intro

Denoising has been shown to improve detection training by injecting GT-initialized noisy anchors as extra supervised queries. This experiment extends the denoising framework to the map, prediction, and planning heads to test whether the same benefit generalizes.

## Method

**Map DN** (`SparsePoint3DTarget.get_dn_anchors`):
- Implemented `get_dn_anchors()` in `SparsePoint3DTarget`, mirroring the detection DN structure.
- GT map polylines are normalized to [0,1] BEV space, then perturbed with noise (`dn_noise_scale=0.1`, ≈3m in BEV).
- 3 positive DN groups + negative DN (larger noise) are created per frame.
- DN anchors flow through the full Sparse4DHead decoder and are supervised with the existing DN loss infrastructure.
- Config: `sparsedrive_r50_stage1_8gpu_noflash_dndetmap` (base: dn config which already has det DN at `num_dn_groups=5`).

**Prediction DN** (`MotionPlanningHead._build_dn_pred_queries`):
- GT agent future trajectories are perturbed with Gaussian noise (`dn_pred_noise_scale=0.5`, `num_dn_pred_groups=3`).
- Each DN group produces one token per GT agent: zero-initialized instance feature, zero anchor embed, and a mode query encoded from the noisy trajectory's cumulative endpoint via `motion_anchor_encoder`.
- Token layout in the decoder: `[agents | ego | DN_agents | DN_egos]`. DN tokens flow through the full GNN/temporal/cross-attention decoder as queries (normal tokens are always keys — no DN contamination of normal attention).
- At the final refine layer, DN agent features are combined with their 1-mode queries and passed through `motion_reg_branch` to produce trajectory predictions. These are supervised with cumulative L1 loss against GT (`dn_pred_loss_weight=1.0`).
- Config: `sparsedrive_r50_stage2_4gpu_bs24_dnpred` (base: vanilla stage2 baseline).

**Planning DN** (`MotionPlanningHead._build_dn_plan_queries`):
- GT ego future trajectory is perturbed with noise (`dn_plan_noise_scale=0.5`, `num_dn_plan_groups=3`).
- Each DN group produces one ego token: zero-initialized feature, ego anchor embed tiled from the real ego, and a 1-mode query from the noisy trajectory's cumulative endpoint via `plan_anchor_encoder`.
- DN ego tokens flow through the full decoder alongside the real ego token. The real ego token slice (`[num_anchor:num_anchor+1]`) is used exclusively for the normal plan head; DN ego tokens are separated out after the loop.
- Supervised with cumulative L1 loss (`dn_plan_loss_weight=1.0`).
- Config: `sparsedrive_r50_stage2_4gpu_bs24_dnplan` (base: vanilla stage2 baseline).

**Key design choice**: DN tokens flow through the full GNN/temporal/cross-attention decoder, giving them contextual features before regression. No attention mask is needed because GNN keys are always the normal top-k tokens — DN tokens never appear as keys. The refine step explicitly slices only the real ego token so DN tokens do not corrupt the normal plan head. Only 1 trajectory mode is used per DN token (vs. `fut_mode=6` for normal agents), initialized from the noisy GT endpoint.

## Discussion

**Prediction DN (DGX job 3606) — complete.** dnpred produces marginal gains over the baseline: NDS 0.529 vs 0.523 (+0.006), mAP 0.417 vs 0.413 (+0.004), car_epa 0.496 vs 0.492 (+0.004). Planning L2 is 0.628 vs 0.636 (−0.008) and collision is essentially flat (0.135% vs 0.133%). The detection and motion improvements are small but consistent, suggesting prediction DN provides a mild regularisation benefit. However, the planning gain is negligible — prediction DN alone is not sufficient to drive L2 meaningfully. A Narval replication (job 59564082) showed consistent NDS/mAP (0.530/0.418) before the job crashed (training exitcode 1 after ~5h); no eval was run so planning metrics are unavailable for this run.

**Planning DN (DGX 3607 + Narval 59605629) — complete.** dnplan is worse than the baseline across all metrics. DGX: NDS 0.519 vs 0.523 (−0.004), mAP 0.404 vs 0.413 (−0.009), car_epa 0.488 vs 0.492 (−0.004), L2 0.674 vs 0.636 (+0.038), obj_box_col 0.123% vs 0.133% (≈flat). Narval replication (59605629) is consistent: NDS 0.526, mAP 0.413, L2 0.670, obj_box_col 0.111%. Both runs agree that planning DN degrades detection and planning relative to the baseline. The noisy ego trajectory queries likely interfere with the normal plan head during stage-2 training rather than regularising it. Planning DN should not be pursued further.

**Map DN (dndetmap, stage1) — in progress.** Training on Apollo crashed repeatedly due to OOM in the eval hook's `collect_results_cpu` gather step (CUDA deserialization of val results from all 8 ranks exhausts GPU memory). Fixed by disabling the eval hook entirely in the config (stage 1 only needs the checkpoint). Training resumed from iter_8780; no eval metrics yet.
