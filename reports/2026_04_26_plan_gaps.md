## Abstract

After five interventions across `plan_relevance`, `plan_aux`, and `plan_unified` all regressed or were null, the bottleneck is not the detection-planning interface, perception-side feature shaping, or planning-aux predictions. This report inventories the remaining promising directions, drawn from gaps to HiP-AD, DiffusionDrive, DeMo, and DriveTransformer plus structural fixes to the current best model (`planpredtrajdeformmm_planinstfeat_laststage`, L2=0.522 / CR=0.047%). Highest-leverage candidates: soft-target mode supervision, more modes with diversity regularization, no-early-aggregation, and stage-1 planning supervision.

## Intro

The current best stage-2 planner is `planpredtrajdeformmm_planinstfeat_laststage` (L2=0.522, CR=0.047%). Recent attempts to push beyond it via auxiliary perception supervision (`detrel_s2`), planning aux heads (`planaux_da`, `planaux_conf`), or planning↔detection coupling (`alldet`, `bidir`) all regressed or were null. The mechanism gap to current SOTA approaches is now in the planner's own *output structure*, *supervision*, and *mode-modeling* — not in how it accesses perception.

Question:
- Among the remaining unexplored mechanisms, which are highest-leverage for L2 / CR given that interface-level changes have failed?

## Discussion

All three Batch B interventions regressed planning vs. the same-server Killarney baseline (3282987, L2=0.4988, obj_box_col=0.063%). Detection metrics stayed flat across the board (NDS within ±0.005, mAP within ±0.001), confirming the changes are isolated to the planner.

- **`modes20diverse` (job 3293230): worst CR.** L2 0.4988 → 0.5361 (+0.037), `obj_box_col` 0.063% → 0.119% (+0.056pp, ~1.9× baseline). Going from 6 → 20 plan modes per cmd with new k-means anchors and a pairwise-similarity diversity reg did not improve trajectory accuracy and roughly doubled the collision rate. Motion-prediction metrics ticked up slightly (`car_ade` 0.6228 → 0.6085, `ped_epa` 0.4302 → 0.4360). The 60-mode plan output (3 × 20) is harder to discriminate at the cls layer, and the diversity reg likely pushed modes apart enough that the cmd-correct slice rarely contains the GT trajectory shape — winner-takes-all then trains on a poorer match.
- **`noagg` (job 3293232): mildest regression but still net-negative.** L2 0.4988 → 0.5246 (+0.026), `obj_box_col` 0.063% → 0.091% (+0.028pp). Bypassing the softmax aggregation and additively blending per-mode attended features into `motion_mode_query` / `plan_mode_query` did not preserve a useful signal — even though the mode-distinct features survived into refine, the refine module has not been retrained from scratch to consume them, and the additive blend likely just adds noise to the position-derived mode_query.
- **`modetime36q` (job 3293233): worst L2.** L2 0.4988 → 0.5578 (+0.059, the largest regression in this batch); `obj_box_col` 0.063% → 0.099% (+0.036pp). Per-(mode, ts) queries with shared MLP regressed trajectory accuracy the most. Each query only sees one waypoint's worth of attention; the shared MLP must learn to predict (x, y) without per-timestep specialization. The decoupling cost (no cross-timestep coordination within a mode) outweighed any gain from per-waypoint attention.

**Combined reading.** Batch B targeted three orthogonal axes — mode count + diversity (#7), early-aggregation harm (#8), and shared-query-across-time bottleneck (#9). All three regressed. With Batch A's interventions also pending and the prior `plan_relevance` / `plan_aux` / `plan_unified` batches all null or negative, the pattern is now consistent: every architectural perturbation to the planner regresses both L2 and CR. The bottleneck either lies (a) in something we haven't perturbed (stage-1 backbone, training recipe, or supervision signal beyond mode regression), or (b) in the rescore / cmd-selection at decode time, which is a single fixed mechanism every variant inherits.

### `modetime36q_timeattn` follow-up

Hypothesis: `modetime36q` regressed because it severed intra-mode temporal coupling (per-(mode, ts) MLP outputs separate (x, y) with no cross-timestep MLP sharing). Fix: add a per-mode time-axis self-attention block (one MHA + LN per planning deformable stage, learnable time pos embed) after the standard-branch deformable cross-attn updates `plan_mode_query`. Run on the `ppdeformmm` baseline (no `planifls`, since the user judged the laststage replacement to be a fragile local minimum).

Result (Killarney 3296782): **L2=0.5872, obj_box_col=0.096%**, NDS/mAP unchanged. **Worse than the original `modetime36q`** (L2 0.5578 → 0.5872, +5.3% relative); ~17.7% relative L2 regression vs. the Killarney `planifls` baseline (0.4988) and ~8.3% vs. the cross-host `ppdeformmm` reference (0.542). CR essentially flat at the modetime36q level. Detection metrics unchanged.

Three things this tells us:

- **The temporal-coupling diagnosis was wrong, or at least not the binding constraint.** Adding a dedicated per-mode time self-attn that sees all 6 timesteps of a mode at once should have fixed cross-timestep coordination if that was the issue. It didn't. The L2 went *further* in the wrong direction. The actual binding constraint of `modetime36q` is more likely the per-(mode, ts) MLP output shape itself — predicting (x, y) per-query without ever sharing parameters across timesteps for the *output projection* loses representational capacity that one MLP outputting all 12 dims at once provides.
- **The `ppdeformmm` (no planifls) baseline is genuinely weaker than `planifls` on this host.** The cross-host `ppdeformmm` reference is L2≈0.542; `modetime36q_timeattn` reached 0.587 on the same `ppdeformmm` family on Killarney. Even accounting for run-to-run variance, removing `planifls` doesn't open up the optimization landscape — it just removes the L2 lever the laststage substitution provides.
- **A clean DeMo-style fix would need separate mode and state decoders, not a small MHA bolt-on.** The full DeMo design (#19) keeps mode queries and state queries as distinct streams and decodes them through dedicated decoders. The bolt-on time-attn here keeps everything on the same `(mode, ts)` flat axis and only adds 6-token self-attn — too thin to recover the lost capacity.

**Implication for #19 (full DeMo):** still gated, and the gating now has stronger negative evidence. The "lighter bridge" failed twice (`modetime36q` and `modetime36q_timeattn`); the heavier bet is unlikely to work without a substantially different output decoder, not just decoupled queries.

## Future Work

### Batch D — Anchor scaling (submitted, two parallel configs)

Re-reading `modes20diverse`'s failure against HiP-AD's reference (`HiP-AD/projects/mmdet3d_plugin/models/plan/instance_bank.py`, `hipad_b2d_stage2.py`): the failure was **not** "more anchors hurts." HiP-AD scales to ~480 anchors via 10 stratified k-means groups (temp/spat/speed) and works. The difference is that HiP-AD never uses a diversity reg — they get diversity *for free* from clustering each group on a different GT subset, so each anchor stays tight against its own sub-distribution. Our `modes20diverse` paid the count cost by pushing anchors away from the data distribution via the diversity penalty, ending up with many anchors that were *farther* from any real GT than the original 6.

Two parallel experiments isolate this:

| # | Config suffix | Change | Hypothesis |
|---|---|---|---|
| D1 | `_modes12` | `ego_fut_mode` 6 → 12, single new `kmeans_plan_12.npy` from full GT distribution (`tools/data_converter/gen_kmeans_plan_12.py`), **no diversity reg** | If this improves or holds, diversity reg was the failure cause in `modes20diverse`, not mode count. If this regresses, mode count itself is binding. |
| D2 | `_modesspeedstrat` | Two anchor groups: low-speed (`<3 m/s`) and high-speed (`≥3 m/s`) bucketed by `\|\|ego_status[6:8]\|\|` at the current frame, each with its own 6-mode k-means file built on the GT subset in that bucket (`tools/data_converter/gen_kmeans_plan_speedstrat.py`). `MotionPlanningHead.plan_anchor` accepts a list of paths; the two `(3, 6, 6, 2)` files are concatenated along the mode axis to `(3, 12, 6, 2)` at init. Single shared `plan_reg_branch`, no per-bucket gating at runtime. | Per-anchor precision is preserved (each bucket's k-means sees a tighter distribution). HiP-AD's lightest stratification recipe. |

Both run on `ptaux2d_ppdeformmm_planifls` Killarney baseline (`L2=0.4988`, `obj_box_col=0.063%`) for matched same-host comparison with all prior Batch A/B work. `planifls` is empirically the stronger baseline on Killarney (the `modetime36q_timeattn` follow-up confirmed removing it is a net loss on this host).

Step 3 (per-group reg branches, full HiP-AD-lite) gated on D2 landing. DeMo-style decoupled queries deprioritized — too much architectural refactor for our parameter budget.

#### Batch D results

Both ran on the `ptaux2d_ppdeformmm_planifls` Killarney baseline (3282987, L2=0.4988, obj_box_col=0.063%). Both regressed L2 and CR; detection metrics flat (NDS within ±0.005, mAP within ±0.001). Motion forecasting (car_ade / ped_ade / ped_epa) ticked slightly *better* on both, same pattern as `modes20diverse` and `modetime36q` — agent-side queries benefit cheaply from extra capacity, but the planning side regresses.

- **D1 `modes12` (3302033): L2 0.4988 → 0.5278 (+0.029), obj_box_col 0.063% → 0.082% (+0.019pp).** Mode count alone, with no diversity reg and a full-distribution k-means, did *not* recover the baseline. This rules out "diversity reg was the only cause of `modes20diverse`'s failure" — even diversity-free, doubling modes hurts. CR is meaningfully better than `modes20diverse` (0.082% vs 0.119%), confirming that the diversity penalty was making `modes20diverse` *additionally* worse on collisions, but the underlying mode-count cost remains.
- **D2 `modesspeedstrat` (3302034): L2 0.4988 → 0.5548 (+0.056), obj_box_col 0.063% → 0.070% (+0.007pp).** Speed-bucketed clustering produced the best CR among all 12+-mode variants (0.070%, only +0.007pp over baseline) but the worst L2 of the four mode-scaling experiments (0.5548). The improved CR is consistent with the hypothesis that bucketed clusters keep each anchor tight against its sub-distribution (fewer collision-prone outliers). The worse L2 suggests the model has trouble selecting between low-speed and high-speed clusters at decode time without an explicit speed-aware gate — winner-takes-all training over 12 anchors produces a flatter logit distribution when ~half the anchors don't match the current speed regime.

**Combined reading.** The mode-count cost is real and orthogonal to the diversity-reg cost. Increasing per-cmd modes from 6 → {12, 12-speedstrat, 20-diverse} consistently worsens L2 by +0.029 / +0.056 / +0.037 (12 best, 20-diverse middle, speedstrat worst). HiP-AD's stratification recipe doesn't transfer one-to-one because they pair stratified anchor groups with per-group reg branches and per-group attention queries — our shared-branch one-shot port loses the precision benefit at the decoder rather than at the anchor stage.

**Implications for next steps:**

- **Drop further per-cmd mode-count scaling** without per-group reg branches. The cheap port has been tested twice (modes20diverse, modesspeedstrat) and a no-diversity baseline (modes12); all three regressed.
- **Per-group reg branches (Step 3 in the original Batch D plan)** — D2's CR improvement *is* a positive directional signal at constant L1 budget. The natural next step is to keep the speedstrat anchors and add a per-bucket reg branch so each branch only sees its bucket's anchors. Cost: ~2× MLP params on the planning head; one config.
- **Rescore path investigation moves up.** The CR-vs-L2 trade-off in D2 (best CR, worst L2 in the 12-mode group) suggests the rescore step in `HierarchicalPlanningDecoder` is biasing the L2 winner away from the closest GT-distance mode when more anchors are available. A no-rescore eval of D2's checkpoint is a single config flip + re-eval (no retrain) and would tell us whether the L2 regression is a decode-time selection problem or a training-time supervision problem.

#### Batch E discussion

- **E0 same-host control (3311242).** Killarney `_laststage` reaches `L2=0.5302, obj_box_col=0.054%`. That's `+0.008 L2 / +0.007pp CR` versus the cross-host `_laststage` reference (`0.522 / 0.047%`) — within typical cross-cluster noise. Detection (`NDS=0.5248, mAP=0.4133`) matches the reference closely. This Killarney baseline anchors all E1/E2 deltas.
- **E1 `_pts12` (3311240): null on L2, mild CR regression.** Doubling planning-deformable sampling points from 6 to 12 gives `L2=0.5270` (essentially identical to the Killarney baseline `0.5302`, −0.003) but `obj_box_col=0.071%` (+0.017pp). Detection unchanged. Adding sampling capacity to the planning deformable does not improve trajectory accuracy and slightly worsens collisions — likely because the additional offsets sample further from the planning anchor box and pick up irrelevant image evidence. **Drop further `num_learnable_pts` scaling.**
- **E2 `_nodetmap` (3311241): better L2, worse CR.** Zeroing perception K/V (`num_det=0, num_map=0, skip_perception_kv=True`) gives `L2=0.5153` (−0.015 vs same-host baseline) and `obj_box_col=0.086%` (+0.032pp). Detection metrics flat. The L2 *improvement* is striking — removing perception K/V helps trajectory accuracy on the laststage architecture, the opposite direction from the prior `ptaux2d_ppdeformmm_planifls_nodetmap` result (`0.5215` vs `0.4988` baseline, +0.023). The CR regression matches the prior finding. **Combined reading**: on the laststage architecture, the perception K/V channel is *net-negative* on L2 — the planning deformable + image features are sufficient, and the perception tokens act as noise. The `+0.032pp` CR cost is the price paid for that L2 gain; rescore presumably loses some of the corner-in-box signal it would have leveraged from K/V-derived agent positions.
- **Joint reading with prior `nodetmap` evidence.** Two architectures, opposite L2 sign:
  - `ptaux2d_ppdeformmm_planifls_nodetmap` (no laststage, planifls present): L2 +0.023 (worse).
  - `_laststage_nodetmap`: L2 −0.015 (better).
  
  The difference must be in the laststage replacement. In the `_planinstfeat_laststage` variant, the final-stage ego query is replaced by `ego_feat_exp` (sourced from the temporal instance bank), which means the planner's final-stage K/V cross-attention to perception tokens overwrites whatever query state had built up. Removing those perception tokens leaves the laststage planner reading purely image features through the deformable, which apparently converges to a tighter L2 minimum on this base. On the non-laststage `_planifls` base, the perception K/V still contributes a small positive L2 signal because the planning query state is preserved across stages.

**Implications:**
- The "perception K/V is essentially redundant" claim in `2026_04_28_paper_plan.md` is *strengthened* on the laststage architecture (L2 actually improves on removal), but with a CR caveat that should be flagged in the paper.
- A laststage + nodetmap + retained rescore variant might Pareto-dominate the current best on L2 if the +0.032pp CR can be partly recovered. Worth a same-host repeat with seed variation before drawing conclusions.

### Batch F — Single-channel K/V disambiguation + map-head-off + rescore diagnostics

The `_nodetmap` family bundles two interventions (det K/V off + map K/V off). Combined with the asymmetric L2 sign across architectures, this leaves the binding question unanswered: is map K/V or det K/V responsible for the L2 effect, and which owns the +0.032pp CR cost? Batch F disaggregates.

**Naming clarification.** Two distinct interventions get conflated under "nomap":
- **head-off**: head module is not built (no perception loss → no backbone gradient pressure → also no K/V).
- **K/V-off**: head trained as usual, but `skip_perception_kv` blocks tokens into the planner's `cross_gnn`/`gnn` op. This is the `_nodetmap` family.

Batch F separates these for the det channel and tests the map-head-off case on the modern stack.
